# Project Structure

## Implemented — current foundation

- `frontend/` is a React, Vite, and TypeScript application with a recruiter-facing Job Description form, a synthetic company-policy knowledge-source panel, and a generated draft view with policy citations and a human-review notice.
- `backend/` is a modular FastAPI application. It currently provides centralized settings, CORS configuration, automatic OpenAPI documentation, and `GET /api/v1/health`.
- `backend/app/db/` provides one shared SQLAlchemy `DeclarativeBase` and lazy factories for an async PostgreSQL engine and sessions. `DATABASE_URL` is optional during application import, is stored as a secret value when configured, and must use the `postgresql+asyncpg` scheme. SQL parameter values are hidden in engine diagnostics; importing the models or application does not connect to PostgreSQL.
- `backend/app/db/models/knowledge.py` implements the Database Design v1.3 `KnowledgeDocument` and `KnowledgeChunk` relationship as `knowledge_documents` and `knowledge_chunks`. Each document records one source version, collection (`knowledge_type`), title, and content hash; `source` is an opaque UUID, not a path. Each chunk retains its citation, index, hash, text, token count, heading paths, BGE model identity, and `Vector(384)` embedding. JSONB holds only heading-path metadata. A composite foreign key requires each chunk and its parent document to have the same collection. Unique constraints protect source versions, citations, and document/chunk indexes.
- `backend/app/repositories/company_policy.py` accepts validated company-policy source metadata, prepared chunks, and finite normalized 384-dimensional vectors. It verifies source/hash/citation/order consistency before opening a session, then stores the complete source version in one transaction. Duplicate versions are rejected without overwriting; failures roll back the whole batch. It does not chunk, embed, log policy content, or invoke an LLM. No API or JD workflow calls this repository yet.
- `CompanyPolicyRepository.find_nearest_chunks(document_id, query_vector, top_k=4)` implements exact pgvector cosine-distance retrieval for one explicit stored document/version. Both source and chunk queries filter `company_policy`; chunks also require `BAAI/bge-small-en-v1.5`. Query vectors reuse persistence validation, and `top_k` must be an integer from 1 to 5. Results are ordered by cosine distance ascending, then chunk index and citation ID. Invalid cosine distances are excluded. The method reconstructs immutable `RetrievedPolicyChunk` objects with validated source/citation/hash/heading metadata, without raw embeddings or arbitrary database metadata. Policy text remains untrusted reference data. Errors are controlled and do not echo policy text, vectors or database details. There are no approximate vector indexes; the repository does not perform request-to-embedding orchestration.
- **Implemented and verified — 06 Oct 2026:** exact cosine retrieval passed a live smoke test on disposable, localhost-only PostgreSQL 17.11 with pgvector 0.8.6. Three synthetic chunks with distinguishable vectors verified nearest-first ordering, bounded `top_k`, repeated tie ordering, source/citation metadata and embedding-free results. Another version of the same source remained isolated, and a Technical Reference document was rejected by the Company Policy query. The temporary container was removed afterward. The JD workflow still uses deterministic lexical demo retrieval.
- `backend/alembic/` contains a PostgreSQL-only migration environment and the first knowledge-table revision. It enables the `vector` extension before creating the tables, with no approximate vector indexes. Migration code, offline SQL, and live migration application are tested. From `backend/`, `python -m alembic upgrade head --sql` previews SQL without a database or credentials. Applying `python -m alembic upgrade head` to another environment requires a configured PostgreSQL service with pgvector installed and migration privileges. Application credentials should have narrower permissions than migration credentials. Downgrade drops the knowledge tables but retains the shared extension.
- **Implemented and verified — 06 Oct 2026:** the pgvector persistence foundation passed live validation using a disposable, localhost-only PostgreSQL 17.11 instance with pgvector 0.8.6. Validation confirmed actual `alembic upgrade head`, the enabled `vector` extension, `knowledge_documents` and `knowledge_chunks`, `Vector(384)`, a real synthetic repository write/read through a fresh session, duplicate rollback behavior, collection foreign-key enforcement, and downgrade/re-upgrade. The temporary test container was removed afterward. This verifies persistence, not a complete semantic RAG workflow or a production database deployment.
- `backend/app/services/` and the integration packages other than `integrations/llm/` remain boundaries for future code; repositories other than the company-policy writer remain planned.
- `backend/app/rag/` contains validated internal company-policy source and chunk contracts, deterministic heading-aware text chunking, and an explicitly synthetic deterministic lexical retrieval adapter for the trainer demo. This adapter is not semantic or vector retrieval.
- `backend/app/rag/embeddings.py` provides a replaceable embedding protocol, a lazy local `BAAI/bge-small-en-v1.5` adapter, and a BGE tokenizer counter. It returns validated, normalized 384-dimensional vectors, prefixes retrieval queries only, and rejects text exceeding the model's 512-token limit instead of truncating it. Model loading happens only on explicit embedding or token-counting calls; importing the application does not load or download the model. The counter can share the encoder's model/tokenizer and excludes special tokens from chunk counts. This layer is not connected to the JD workflow or lexical demo retriever.
- `backend/app/rag/semantic_retrieval.py` implements a standalone `SemanticCompanyPolicyRetriever` compatible with the existing retriever interface. It converts validated job requirements into a deterministic, fixed-order query with explicit labels for title, summary, responsibilities, skills and supplied optional fields. It calls the injected local `EmbeddingService.embed_query()` using `asyncio.to_thread`, then delegates to the repository's exact cosine query for one configured document UUID and `top_k` (default 4, bounded 1–5). The embedding service adds the BGE instruction; the adapter does not add it again. Results pass through as the existing immutable `RetrievedPolicyChunk` tuple. Construction/import does not load a model or create/connect a database engine. Query-construction, embedding and unexpected retrieval failures are sanitized; existing controlled repository errors are preserved. No request, policy content or vectors are logged.
- Semantic query text is not summarized, clipped or silently truncated. This simple strategy preserves the supplied requirements, but a valid long JD request may exceed BGE's 512-token budget. The embedding service checks the complete input, including its instruction and special tokens, and the adapter returns a controlled retrieval error before encoding or database search when that limit is exceeded.
- **Implemented and verified — 06 Oct 2026:** standalone request-to-BGE-to-pgvector semantic retrieval passed with the cached/local BGE model and a disposable, localhost-only PostgreSQL 17.11/pgvector 0.8.6 instance. Three synthetic policy sections used real tokenizer-aware chunks and normalized 384-dimensional document embeddings. A synthetic privacy-engineering request used real BGE query encoding and ranked Privacy and Data Protection first. Validation confirmed the configured two-result limit, source/citation metadata, explicit document/version scoping and no returned embeddings. The temporary container was removed afterward. This adapter is not connected to the JD LangGraph, API or UI; the trainer-facing workflow remains lexical.
- `chunk_company_policy_for_semantic_retrieval()` in `backend/app/rag/chunking.py` prepares deterministic, citation-bearing company-policy chunks using BGE tokenizer counts: at most 400 tokens including headings, with up to 50 tokens of overlap at word boundaries and no tokenizer truncation. It reuses the existing chunking algorithm and uses only the embedding service's tokenizer, without generating vectors. The generic default remains 700/75; the lexical demo continues to explicitly use 500/50 with whitespace counting. This preparation helper is not semantic retrieval and is not wired into the JD workflow.
- `backend/app/agents/jd/` contains a bounded three-node LangGraph workflow that retrieves synthetic demo policy context, invokes the Groq integration, validates model citations, and returns an unapproved job-description draft. It does not persist or approve the draft.
- `backend/app/integrations/llm/` contains the Groq structured-output adapter used by the Job Description workflow. The API key remains optional during application startup and is required only when generation is invoked.

## Planned — future functionality

- `backend/app/agents/` contains four bounded workflow packages: `jd`, `screening`, `copilot`, and `evaluation`. The `jd` package has the limited trainer-demo workflow described above; the other three remain planned. They are Python modules inside the FastAPI modular monolith, not separate microservices.
- Other ORM business models, a production Docker Compose PostgreSQL service, other repositories, and a LangGraph PostgreSQL checkpointer remain planned. The disposable database used for the successful live validation does not implement the production service.
- JD LangGraph integration of the standalone semantic adapter, API/UI semantic-retrieval replacement, production/private policy ingestion, active-policy selection and replacement/deletion lifecycles for obsolete versions remain planned. Local embeddings, BGE tokenizer-backed chunk preparation, knowledge persistence, exact vector queries and the semantic adapter provide standalone semantic retrieval; they are not connected to JD generation yet. The application must explicitly choose a stored document/version; there is no automatic active/latest selection. CVs and transcripts do not belong in either knowledge collection. Production Docker Compose remains planned as noted above.
- Background processing and concrete external integration implementations remain planned; their current packages are architectural boundaries only.
- `job-publishing-mcp/` marks the boundary for a future lightweight, TalentTrace-owned MCP server for approved job publishing. It is not implemented.

Authentication, business-data persistence, human approval/revision, the remaining hiring workflows, and other external integrations remain planned work.
